## The defect

`load_adapter_weights` audits the adapter's **keys** and **shapes**. A wrong `r` changes tensor
shape and is caught. A wrong `alpha` changes no shape at all — it only moves
`LoRALinear.scale = alpha / r`, the single multiplier `forward` and `merge` both read. Three
consumers inject with `LoRAConfig()` **defaults** rather than the artifact's own config, so an
adapter trained at a different alpha would be applied at the wrong magnitude, silently, with no
error and no shape mismatch:

- `scripts/phase14_recall.py:530` — inside `load_adapted_model`, which `phase16_persistence.py:2741`
  calls and Phase 17 will call
- `scripts/phase14_recall.py:1448` — `run_bit_identity_control`
- `scripts/personalize_demo.py:431` — `build_demo`

Benign today only by coincidence: the committed `checkpoints/persona_adapter.pt` carries
`{'r': 8, 'alpha': 16.0, 'dropout': 0.0, 'targets': (...)}`, which equals `LoRAConfig()`.

## Task 1 — audit the scale at the choke point

**Files:** `src/personacore/lora/inject.py`, `tests/test_lora_inject.py`

Reading the config at the three call sites fixes today's callers. It does not stop a fourth
caller — a Phase-17 script — from reintroducing the same line. `load_adapter_weights` already
receives the **whole artifact**, `lora_config` included, and every consumer already routes through
it. One audit there covers all present and future callers.

**Action:** after the key audit and the shape audit, before `load_state_dict`, compare every
`LoRALinear.scale` in the model against `artifact["lora_config"]["alpha"] / ["r"]`. Exact float
equality is correct and deliberate: `LoRALinear.__init__` computes `alpha / r` with the same
operation on the same operands, so equal inputs give a bit-identical float; a tolerance would only
weaken the check.

Skip the audit when `artifact` carries no `lora_config` — `tests/test_lora_inject.py:133` applies
one model's `lora_state_dict` directly onto another, where no artifact and no config exist. This
is not an escape hatch for real artifacts: `checkpoint.load_adapter:246` raises `ValueError` when
`lora_config` is absent, so anything read off disk always carries it.

**Verify:** new test builds an r=4/alpha=16 model (scale 4.0), hands it an artifact whose
`lora_config` says `alpha=32.0` (scale 8.0), asserts `ValueError` — plus a positive control that
the artifact's own config still loads, so the test cannot pass against an audit that rejects
everything. Mutation-check: a copy of the module with the audit stripped must load that same
drifted artifact SILENTLY, which is the pre-fix behaviour and proves the refusal comes from the
audit and nothing else.

**Done:** `.venv/bin/python -m pytest tests/test_lora_inject.py -q` green.
