**(d) The `batch_fn` branch.** Add a `fact_bin is not None` branch to the dispatch at `:402-452`,
placed so it takes precedence over the mask branch. It must resolve **both** PATTERNS traps:
  - **The step counter is a GLOBAL MICRO-STEP counter, assembled from two halves.**
    `get_batch_fact_aligned` computes `fact_index = step % n_facts`, and its reference caller
    `scripts/phase21_unit_record.py` advances `step` once per **micro-step**. So the value handed to
    the loader must advance once per micro-step too:
    `step=_fact_cursor["step"] * n_facts + micro`.
    The optimizer-step half is not in the closure — `step` lives at `loop.py:507` and advances in the
    `while` loop — so capture a small mutable cell defined before the dispatch, e.g.
    `_fact_cursor = {"step": 0, "seen": []}`, and update `_fact_cursor["step"] = step` at the top of
    each `while` iteration, before `_optimizer_step` is called. The micro half is `batch_fn`'s own
    `micro` argument, which the synthetic branch at `:450-452` already uses.
    **Two comments are mandatory here, because both errors are silent:**
      1. Why the cell and not a closure over the loop variable — a closure captures the binding at
         definition time, not the value at call time; the cell is the minimum change.
      2. **Why `* n_facts + micro` and not the bare optimizer step.** With `_fact_cursor["step"]`
         alone, `fact_index = step % n_facts` is CONSTANT across the whole `for micro in range(accum)`
         window, so at `accum == n_facts` ONE record is clipped and summed `n_facts` times per
         optimizer step. True per-record sensitivity becomes `n_facts*C` while the accountant is told
         `C` — DPSGD-04's wrong-sensitivity fake arriving from the wiring, and **invisible to all four
         D-16 invariants**: each drawn record is still individually clipped to `C`, the drain still
         fires, the write count is still 1, and the generator still advances. With
         `* n_facts + micro`, `fact_index == micro` and the window covers exactly
         `set(range(n_facts))`.
  - **Three return values against a two-value unpack.** `_optimizer_step:170` does
    `xb, yb = batch_fn(micro)`. The branch's closure calls
    `get_batch_fact_aligned(train_bin, train_mask_bin, fact_bin, model_cfg.block_size,
    runtime.device, step=_fact_cursor["step"] * n_facts + micro, n_facts=n_facts)`, appends the
    returned `fact_index` to `_fact_cursor["seen"]`, and returns `(x, y)` — exactly two values.
    **Do not change `_optimizer_step`'s unpack**; every other `batch_fn` returns two values and
    widening the contract for one branch would touch four call sites for no gain.
  - **The one-record-per-micro-step refusal.** After the accumulation window, refuse (`ValueError`)
    unless the collected `fact_index` values for that step are exactly `set(range(n_facts))` — i.e.
    every fact contributed exactly once. Under (d)'s counter this holds by construction of the
    counter, which is the point: the check is not there to catch the counter, it is there to catch
    **the loader** returning something else (a mis-built bin, a future loader edit, or a fact map
    whose ids are not `0..n_facts-1`). Message names Phase 21 D-02: one micro-step IS one privacy
    record under ragged fact-aligned accumulation, and that claim is what makes ordinary backward
    hand back the per-record gradient. Clear `_fact_cursor["seen"]` at the start of each step. This
    turns SC2's prose into a runtime property at the cost of a list append per micro-step.

**(e) Docstring.** `fact_bin`'s Args entry copies `replay_bin`'s register at `:252-291` — what the
