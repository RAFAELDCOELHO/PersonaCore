Add to `src/personacore/training/data.py` — beside `get_batch_memmap_masked`, not inside it:

`def fact_window_impurities(fact_ids, block_size, *, space="input")` -> `list[int]`, the indices of
every `block_size`-aligned window carrying more than one distinct fact id. Pure numpy, no I/O, no
torch.

Length contract, stated in the docstring and enforced by a raise: the aligned bins carry
`n_windows * block_size + 1` elements. The trailing `+1` is the LABEL-SHIFT TAIL — one pad slot so
that every window's target slice `[k*B+1 : (k+1)*B+1]` is in range for all `k`, which is what makes
the target-space claim assertable DIRECTLY over all `n` windows instead of inferred from three
premises. So the raise is on `(len(fact_ids) - 1) % block_size != 0`, and its message names the
observed length, the block size and the remainder. A truncate-by-1 adversary (A4) therefore fires
THIS assertion rather than the purity loop, and the message must make that distinguishable.

`space` is keyword-only and takes exactly two values, `"input"` and `"target"`, DEFAULTING TO
`"input"`:
  - input space:  `fact_ids[:-1].reshape(-1, block_size)`
  - target space: `fact_ids[1:].reshape(-1, block_size)`
A window is impure iff `np.unique(row).size != 1`. There is NO `"both"` mode and NO union. The two
spaces answer different questions, and a union default makes the predicate refuse every CORRECTLY
built bin — proof-7 would then abort every aligned build. Raise `ValueError` on any other `space`.

`"input"` is the default because it is D-05/SC2's claim verbatim: ROADMAP SC2 says *"no
`block_size`-aligned window contains token ids from two fact shards"*, which is a statement about the
WINDOW, i.e. input space. Proof-7's `== []` assertion, the loader's run-time check (plan 21-06) and
the A0-A5 expectations all use it.

MEASURED, and it is why the default is a correction rather than a preference: window `k`'s target
slice is `fact_ids[k*block_size + 1 : (k+1)*block_size + 1]`, whose LAST element is index
`(k+1)*block_size` — the FIRST token of window `k+1`. When window `k` is a fact's last window that
element belongs to the NEXT fact, so on a CORRECT bin `space="target"` returns exactly `n_facts - 1`
rows, never `[]`. On the `BLOCK = 4` fixture above, `space="input"` on GOOD is `[]` while
`space="target"` on GOOD is `[1, 2]` — the same bytes, two different correct answers.

State the target-space claim CORRECTLY in the docstring rather than dropping it, because it is the
claim that actually supports "one micro-step is one privacy record":

  On a correct bin, target space has EXACTLY `n_facts - 1` boundary rows. Each boundary token is the
  next fact's `<|system|>` token, which carries mask 0 (`src/personacore/dialogue/serialize.py:81`,
  `emit([system_id], 0)`), so `y[m == 0] = -100` (`src/personacore/training/data.py:125`) sets it to
  `F.cross_entropy`'s `ignore_index` and it contributes NOTHING to the record's loss. The label shift
  therefore never leaks one fact's gradient into another record's micro-step.

Encode that as POSITIVE assertions in tasks 2 and 3 — the count equals `n_facts - 1` AND every
boundary token's mask is 0 AND every boundary token's fact id is the next fact's index — never as an
inequality to be waived.

Do NOT add a `fact_window_impurities_masked` variant. The mask restriction is not what makes the
target-space claim work: the boundary crossing is a property of the +1 shift, not of padding, so a
masked variant would be a second predicate with no additional discrimination and one more thing to
keep in agreement.

Record the DERIVED CONSTRAINT in the docstring, because it is a consequence and not a decision, and

that fact's OWN id.** A reserved sentinel would put two distinct ids in every fact's last window in
INPUT space, and sentinel `0` additionally collides with fact index 0 in a `uint16` map. The padding
is masked to 0 anyway (`y[m == 0] = -100`, `:125`), so the id it carries is purely an accounting
label.
