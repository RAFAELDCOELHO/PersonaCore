# Phase 14 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Phase surface (this is not a web app):** one artifact — the offline Gradio 5.50.0 **`gr.Blocks`**
demo `scripts/personalize_demo.py` (DEMO-07), which loads `checkpoints/convbase_slim.pt` +
`checkpoints/persona_adapter.pt` and offers memory **ON/OFF**, **Reset**, and a live
**prompt-token-id panel**. There is no React/Next.js/Vite stack, so the shadcn gate is **not
applicable**. `scripts/demo_app.py` (the Milestone-1 demo) is **not touched by this phase** (D-17)
— it is read here only as the visual and structural precedent.

**Locked shape (do not relitigate):** pre-trained adapter, live toggle + Reset, **no Teach tab**
(D-16). `gr.Blocks`, not `gr.ChatInterface` (D-18: Reset is stateful and destructive, and the token
panel is a second output). Token panel renders from the **same** `build_recall_prompt()` the scoring
harness calls (D-18). Generation-budget slider floors at the census-derived constant (D-19).

## Design System

| Property | Value |
|----------|-------|
| Tool | none (no shadcn — Python/Gradio stack) |
| Preset | not applicable |
| Component library | Gradio 5.50.0 built-ins only: `Blocks`, `Row`, `Column`, `Markdown`, `Chatbot`, `Textbox`, `Button`, `Checkbox`, `Code`, `Slider`, `Accordion`, `Examples` `[VERIFIED: .venv gradio 5.50.0, all present]` |
| Icon library | none (Gradio built-in icons only: chatbot copy button, accordion chevron) |
| Font — body | `ui-sans-serif, system-ui, sans-serif` (OS font stack, zero network) — see Offline Guarantee |
| Font — mono | Gradio default `IBM Plex Mono` — a `LocalFont`, wheel-bundled woff2, no CDN `[VERIFIED: LocalFont, stylesheet url=None, inline @font-face on static/fonts/IBMPlexMono/*.woff2]` |
| Theme | `gr.themes.Default(font=["ui-sans-serif", "system-ui", "sans-serif"])` — the stock theme with **exactly one** variable changed |
| Custom CSS | **none.** `css=` / `css_paths=` / `js=` / `head=` are not used |

**Hard rules for this phase:**
1. **No `css=`, no `js=`, no `head=`, no third-party theme, no GoogleFont.** The one permitted theme
   argument is the `font=` override above, and its only effect is removing a remote stylesheet.
2. The `theme=` object is passed to the **`gr.Blocks(...)` constructor**. `Blocks.launch()` in
   5.50.0 does not accept `theme` `[VERIFIED: "theme" not in launch signature]`; the constructor
   emits a `DeprecationWarning` naming the Gradio-6 migration. The `gradio>=5,<6` pin in
   `pyproject.toml` holds, so the warning is cosmetic — note it in a code comment, do not work
   around it.
3. Everything else is theme-supplied and unmodified.

### Why the font stack is overridden (measured, not stylistic)

`08-UI-SPEC` recorded a hard rule of "no `theme=` argument" justified by "the default theme is the
only offline-verified configuration (wheel-bundled `LocalFont`)". **That justification does not hold
for gradio 5.50.0**, measured first-party this session:

```
gr.themes.Default()._stylesheets
  -> ['https://fonts.googleapis.com/css2?family=Source+Sans+Pro:wght@400;600&display=swap']

gr.themes.Default(font=["ui-sans-serif","system-ui","sans-serif"])._stylesheets
  -> []
differing non-private theme vars between the two: ['font']   # nothing else changes
gr.Blocks(theme=<override>).stylesheets -> []                # confirmed at Blocks level
```

The stock theme's **body** font is a `GoogleFont`, so the served page instructs the browser to fetch
`fonts.googleapis.com`. The server still makes zero outbound calls (analytics kill-switch +
`share=False`), and offline the fetch fails closed with a system-font fallback — but a reviewer who
opens devtools on a demo whose entire thesis is "fully on-device" sees a request to Google. The
override costs one argument, changes exactly one theme variable, leaves the mono `LocalFont`
untouched, and makes the offline claim literal.

**Contract test (CPU-only, no launch, no generation):** `build_demo().stylesheets == []`. Same
structural-enforcement register as D-17's mask-parity test and D-18's byte-identity test — the
offline claim is held by a test, not by a comment.

**This deviates from the M1 hard rule and is listed under Open Decisions for Review.** It does not
change `scripts/demo_app.py`, which stays literally untouched per D-17.

## Copywriting Contract

**Honesty lock (the Phase-14 analog of M1's "no personalization yet — that's Milestone 2").** The M1
lock said what the model *cannot* do. This one says what the demo *is evidence of*, and — equally
important — what it is not:

> **This is a 13.9M-parameter model. Its answers are short and often wrong. What this demo shows is
> WHERE the memory lives — in 331,776 adapter parameters, not in this page's context — not how good
> the model is.**

That sentence is **required verbatim in the header** and in the module docstring. Three claim rules
follow from it, binding on every string in this table:

- **Claimable (structural / measured):** the facts are not in the prompt (the token panel proves it
  live); memory OFF is the un-adapted base (the `enabled` flag gates the delta branch; D-11.3
  measures bit-identity on real weights); the adapter is a 1.35 MB file trained in a different
  process.
- **Not claimable:** any recall rate, any "it remembers everything", any implication that a
  successful answer on screen generalizes. **No numbers appear in the demo UI at all** — the header
  points at `results/phase14_recall_report.md`, which carries taught vs never-seen rates and every
  failure. This makes the UI copy incapable of going stale and incapable of overclaiming.
- **Never shown:** the locked fact values themselves, anywhere in the UI chrome (title, description,
  examples, placeholders, captions). The demo process holds no fact strings — see Error &
  Failure-State Contract.

|---------|------|
| Primary CTA (button) | `Ask` |
| Demo title (`title=` + H1) | `PersonaCore — memory in the weights (13.9M frozen base + 331,776 LoRA parameters, fully on-device)` |
| Header description | `The things this model knows about me are not on this page, not in a prompt, and not in a database. ## Token Panel Contract (D-18)

**Component:** `gr.Code(label="Context fed to the model this turn — exact prompt token ids",`
`language=None, lines=8, interactive=False, wrap_lines=True, show_line_numbers=False)`
`[VERIFIED: language=None is a valid gr.Code language; wrap_lines and show_line_numbers exist in 5.50.0]`

**Render format — identical in every state, three fixed-width lines:**

```
ids  (19) : [8187, 8185, 119, 104, 97, 116, 341, 32, 121, 111, 117, 114, 331, 39, 115, 315, 101, 63, 8186]
decoded   : <|system|><|user|>what is your dog's name?<|assistant|>
source    : build_recall_prompt(tok, question) — the same call the scoring harness makes
```

The id list is produced by `build_recall_prompt` and rendered directly. **No parallel prompt builder,
no re-encoding for display, no pretty-printing that could reorder or elide ids** (D-18). The
byte-identity regression test compares this panel's id list against the harness's committed dump for
the same input.

**Persistent caption below the panel (`gr.Markdown`, body size):**

> `Every turn is built by the same function the scoring harness calls. Your question's ids sit`
> `between <|user|> (8185) and <|assistant|> (8186). Nothing else is ever added — no facts, no`
> `system prompt, no history.`

### Empty / initial state — the panel is POPULATED at startup, never blank

Before any recall has been attempted in the session, the panel shows the **real, computed
empty-question scaffold** — `build_recall_prompt(tok, "")`, evaluated at build time:

```
ids   (3) : [8187, 8185, 8186]
decoded   : <|system|><|user|><|assistant|>
source    : build_recall_prompt(tok, "") — the empty-question scaffold, rendered at startup
```

`[VERIFIED first-party: encode_dialogue(tok, [], [("", "")]) truncated at <|assistant|> returns
exactly [8187, 8185, 8186]; the same call with "what is your dog's name?" returns the 19-token
sequence above, matching 14-RESEARCH F2.]`

**Why this does not read as an error or as a broken feature — four reasons, all deliberate:**

1. **It is real data, not a message.** Three actual token ids, produced by the same function, in the
   same three-line format the panel uses forever after. Nothing about it is a special case.
2. **It is populated.** An empty `gr.Code` block reads as broken; a `"waiting…"` string reads as a
   pending fetch (fatal framing for an offline demo); a disabled/grayed panel reads as a feature
   that is off. A populated panel reads as a panel that works and simply has nothing in it yet —
   which is exactly, literally true.
3. **It makes the phase's point before the first question is asked.** A viewer sees a 3-token
   context — an empty persona, an empty user turn, a handoff — and understands the baseline the
   question gets inserted into. The delta between 3 tokens and 19 tokens *is* the question, visibly.
4. **The caption names it.** `— the empty-question scaffold, rendered at startup` on the `source`
   line, in the same slot that later carries the live provenance. No separate empty-state copy to
   maintain, no state-specific string to drift.

**Rejected alternatives (recorded so they are not reintroduced):** blank panel; `"No turn yet."`
prose inside the code block; hiding the panel until the first turn (a panel that appears late reads
as reactive chrome, not as evidence that was always there).

### Update timing

The panel is written **once per turn, at turn start, before the first generated token**, and is not
touched again during streaming. A reviewer can therefore read the full context while the answer
streams — the two are on screen simultaneously, which is the entire point. Updating it mid-stream
would add motion that competes with the streaming bubble for attention and would imply, falsely,
that the context grows during generation.

## Memory Toggle Visual Contract (DEMO-07)

What changes **on screen** when Memory is toggled. Three surfaces, one of them permanent.

### 1. Status banner — the current state (live)

The `gr.Markdown` banner at the top of the controls column swaps between the three Status strings in
the Copywriting Contract. It is bold, 16px, always in frame, and it is the only element that changes
on toggle. Latency is not a consideration: `set_adapter_enabled` is 36 Python boolean writes, so the
swap is instantaneous by construction — **no spinner, no loading state, no transition**.

### 2. Memory checkbox — the control's own state

Theme-supplied checked/unchecked rendering, accent `#F97316` when checked. This is the affordance;
the banner is the readout. Both are needed: a checkbox alone is too small to read in a screen
recording, and a banner alone gives nothing to click.

### 3. Per-turn stamp — which mode produced which answer (permanent)

**Every assistant bubble carries a stamp as its first line**, captured at turn start and never
rewritten:

```
**memory ON**

i have a dog named zorp.
```

- Rendered by `Chatbot(render_markdown=True)`: a bold 16px line, a blank line, then the streamed
  answer at 14px. It reads as a caption on the answer, not as model output.
- **Present from the very first yield.** The mode is fixed before generation starts, so the stamp
  streams in with the answer rather than appearing after it. In a recording, the label is legible
  during the entire generation, not just at the end.
- The streaming contract is unchanged: the callback yields `STAMP + "\n\n" + accumulated_text`, so
  the bubble still grows monotonically and never flickers fragments (08-RESEARCH Pitfall 1).
- Three literal stamps: `**memory ON**`, `**memory OFF**`, `**memory DELETED**`.

### Prior turns are NEVER re-rendered or re-annotated

Flipping the toggle changes the banner and nothing else. It does not re-generate, re-score,
re-annotate, or gray out any previous answer. Each bubble keeps the stamp of the mode that actually
produced it, forever.

This is the honest behavior *and* the one a demo video needs: ask the same question twice, once ON
and once OFF, and both answers sit in one scrollback, each permanently labelled with its own
provenance. A viewer scrubbing the video at any frame can read which mode produced any visible
answer without rewinding to find the toggle click. Re-annotating history on toggle would be an
outright lie — it would suggest the earlier answer was produced under the current setting.

### At-a-glance summary for a video viewer

| Question | Answered by |
|----------|-------------|
| What mode am I in right now? | the bold status banner, always in frame |
| What mode produced *this* answer? | the bold stamp on that bubble, permanent |
| Did the context change between modes? | the token panel — same ids, same length, both times |

## Generation Budget Slider Contract (D-19)

**Decision: the floor is SURFACED to the user, not a silent clamp.** D-19 already requires a code
comment explaining why the minimum is not zero. That comment serves a future reader of the source. A
reviewer *watching the screen* is the person the floor actually protects — they are the one who would
otherwise drag the slider down, watch an answer get cut off before the value is uttered, and conclude
the memory failed. Explaining it only in a comment they will never open protects the wrong reader.

| Property | Value |
|----------|-------|
| Component | `gr.Slider` inside `gr.Accordion(open=False)` |
| Label | `Max new tokens` |
| Minimum | `RECALL_MAX_NEW_TOKENS` — **imported** from the scoring harness, never re-derived here |
| Maximum | `256` (answers measured at 11–24 tokens, 14-RESEARCH F5; 256 is generous headroom and keeps CPU generation snappy) |
| Default `value` | `RECALL_MAX_NEW_TOKENS` — the demo opens at exactly the harness's setting, so the default UI state **is** the measured condition |
| Step | `8` |

**Accordion label (always visible, even collapsed):**

> `Generation settings — the minimum token budget is fixed by the scoring harness`

**Slider `info` (visible whenever the accordion is open) — exact copy:**

> `The minimum is the exact budget the scoring harness used, derived from the locked fact set's`
> `token census plus documented headroom (see the derivation in scripts/phase14_recall.py). Below`
> `it, an answer could be cut off before the value is uttered — a working memory would look like a`
> `failure. The UI cannot go lower, so no setting on this screen can manufacture that false`
> `negative.`

**Why the accordion is `open=False` and the floor is still "surfaced":** the always-visible accordion
label states that a fixed minimum exists and where it comes from; opening it gives the full
derivation. The demo-video frame stays clean while the question "why can't I go to zero?" is answered
the moment it is asked — which is the moment the user opens the accordion to try.

**The demo never re-derives the constant.** It imports the integer. Re-deriving would require the
locked fact values in the demo process, which this spec forbids (see Error & Failure-State Contract).

## Error & Failure-State Contract

The failure modes below are enumerated exhaustively. Each row either specifies what the user sees, or
states — with reasoning — that the failure is designed to be unreachable from the UI.

### The D-19 fit-guard `SystemExit` is deliberately NOT reachable from the UI

The guard raises when a locked fact's value cannot fit inside the derived generation budget. Its
input is `LOCKED_VALUES`. **The demo process deliberately does not hold the fact values** — not in a
constant, not in a config, not in an example string, not in a comment. That is not an oversight to
work around; it is the clean-room posture. A demo that carries the fact strings in memory is one
careless f-string away from putting one in context, which is precisely the failure PITFALLS-11 exists
to prevent, and it would be self-inflicted at the exact moment the claim is being demonstrated.

So the guard is structurally offline-only: it runs in `scripts/phase14_recall.py`, where the values
legitimately live, at fact-set lock time. Its output crosses into the demo as a single integer. The
demo's entire obligation under D-19 is to floor the slider at that integer and never invent its own.

**What the demo does instead:** it imports `RECALL_MAX_NEW_TOKENS`. If that import fails, it refuses
to launch (next table row) — the one failure in this family that *is* reachable, and it is handled
before a window ever opens.

| Adapter/base **fingerprint** mismatch (`load_adapter` `UserWarning`, warn-not-error per 09-CONTEXT D-02) | build time | **Surfaced in the UI.** The mismatch banner (`gr.Markdown`, `visible=False` by default) becomes visible above the chat and stays for the session: `> **ADAPTER / BASE MISMATCH** — this adapter was trained against a different base checkpoint (expected {git_sha}/{step}/{val_loss}, adapter carries {git_sha}/{step}/{val_loss}). Anything this session produces is not evidence of anything. Retrain the adapter against this base before recording or reporting.` |
| Adapter **key/shape** audit failure (`load_adapter_weights`, 09-REVIEW CR-02) | build time, before any tensor is copied | Raises. Terminal only, no UI — a structurally incompatible adapter cannot produce a meaningful session, so there is nothing to degrade into. |
| Generation failure mid-turn | runtime | Gradio's default error toast, theme-supplied. No custom error UI (same posture as M1). The `(0, 4096]` `max_new_tokens` guard is unreachable: the slider maximum is 256. |
| **State after Reset, no adapter loaded** | runtime | The MEMORY: DELETED banner (Copywriting Contract). The Memory checkbox goes `value=False, interactive=False`; the Reset button goes `interactive=False`; the Ask button, textbox, and token panel stay fully live. **You can still chat** — with the bare conversational base, which is the point of Reset: the model still works, the memory is gone. |
| Toggling Memory after Reset | runtime | **Unreachable by construction** — the checkbox is non-interactive. This is deliberate and is 14-RESEARCH Pitfall 9: after `eject_adapter` the wrappers are gone, so a live toggle would either raise or silently do nothing. Silently re-injecting a fresh `B=0` adapter would be indistinguishable from OFF and would misrepresent what Reset did. A dead-but-visibly-disabled control plus the DELETED banner is the honest rendering. |
| Clicking Reset twice | runtime | **Unreachable by construction** — the same event that ejects sets the button non-interactive. |
| `set_adapter_enabled` refusing on a merged module (`RuntimeError`, 09-REVIEW CR-01) | runtime | **Unreachable by construction** — the demo never calls `merge()`; merging destroys the toggle, which is the demo. Named here because CR-01 exists precisely to catch a dead "memory off" switch. If it ever fires, it surfaces as the Gradio error toast, which is the correct loud failure. |

**Design rule visible in this table:** every failure that would produce a *misleading but functional*
session (fingerprint mismatch) is surfaced **in the UI**, because a terminal warning nobody reads is
exactly how a false demo gets recorded. Every failure that makes a meaningful session **impossible**
(missing checkpoint, shape mismatch, missing budget constant) is raised **before `launch()`**, so no
window ever opens on a broken demo.

## Interaction Contract

| Interaction | Contract |
|-------------|----------|
| Ask | Textbox `submit` and the Ask button `click` bind to the same callback. The textbox clears on submit. |
| Streaming | Callback yields a tuple `(chat_history, token_panel_text)` each step; the assistant message content is `STAMP + "\n\n" + accumulated_text` (cumulative, never fragments — 08-RESEARCH Pitfall 1). The token panel string is computed once at turn start and re-yielded unchanged. |
| Latency expectation | First visible chunk in milliseconds; a ≤ 64-token answer streams in well under a second on CPU (M1 measured ~95–105 tok/s at the same 13.9M size). **Streaming is the loading state** — no spinner, no skeleton. |
| Toggle | `set_adapter_enabled(model, bool)` — 36 boolean writes, instantaneous. Updates the status banner only. Does not regenerate, re-annotate, or clear history. |
| Reset | `eject_adapter(model)` — single click, no confirmation modal (justified in the Copywriting Contract). One event returns: checkbox `value=False, interactive=False`; Reset button `interactive=False`; banner → MEMORY: DELETED. |
| Concurrency | **Every model-touching event shares one `concurrency_id`** so they serialize (14-RESEARCH Pitfall 10: a toggle flip landing mid-generation would produce a half-ON/half-OFF answer whose stamp and token panel both lie). The single-user-local assumption is stated in the module docstring; `share=False` + localhost bounds the exposure. |
| EOS / turn stop | `stop_ids={8184, 8185}` — the pinned idiom. No raw special token is ever rendered in a chat bubble. Special tokens appear **only** inside the token panel's `decoded` line, where showing them is the entire point. |
| Examples | `gr.Examples` fills the textbox; does not submit; no `cache_examples` (caching would run the model at launch). |
| History | `gr.Chatbot(type="messages")`. History is display-only and is **never** concatenated into a prompt — every turn is an independent `build_recall_prompt` call. This is a clean-room requirement, not a stylistic choice, and the token panel proves it every turn (the id length does not grow with conversation depth). |
| Launch | `GRADIO_ANALYTICS_ENABLED=False` set **before** `import gradio`; `analytics_enabled=False` passed; `share=False`; localhost. `RuntimeConfig(device="cpu")` pinned — device resolution must never drift to MPS in the demo path. |
