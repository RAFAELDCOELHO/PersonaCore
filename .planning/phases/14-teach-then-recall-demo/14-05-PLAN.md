<design_note>
**Why `phase14_factset` is imported lazily inside `main()`.** (Full graph and the two cross-script edges: `<import_topology>` below.)

`scripts/personalize_demo.py` must import `RECALL_MAX_NEW_TOKENS` from this module (14-UI-SPEC:
"the demo never re-derives the constant — it imports the integer"), and the hard constraint is that
the demo process must never hold the fact string values in memory. A module-level
`import phase14_factset` would pull every locked value into the demo's address space transitively —
one careless f-string away from putting a fact in context at the exact moment the claim is being
demonstrated.

So this module's **import-time surface holds integers only**. `VALUE_TOKEN_COUNTS` is a tuple of
counts transcribed from `phase14_factset.VALUE_TOKEN_CENSUS`, not a mapping from values. The fact
strings enter only inside `main()`, where they legitimately live. The D-19 fit guard therefore runs
offline in the harness and is deliberately unreachable from the UI — which is exactly what
14-UI-SPEC's Error Contract specifies.
</design_note>

<import_topology>
## AUTHORITATIVE: the Phase-14 script import graph

**This block is the single source of truth for how the four Phase-14 scripts import each other.**
Plans 14-07, 14-08, 14-09, and 14-10 reference it by name; none of them may restate a different rule.

```
phase14_factset      LEAF - pure data + pure functions. Imports nothing from scripts/.
   ^          ^
   | module   | LAZY (inside main() / inside the function that needs values)
teach_persona <-LAZY-> phase14_recall
                            ^
                            | module-level - receives INTEGERS and pure functions only
                     personalize_demo
```

**The five rules:**
1. `phase14_factset` imports nothing from `scripts/`. It is the leaf and stays torch-free.
2. `teach_persona` imports `phase14_factset` at **module level**. It is a training driver and is
   never imported by the demo, so pulling the fact strings in at import time is harmless there.
3. `phase14_recall` imports `phase14_factset` **lazily**, inside `main()` and inside any function
   that needs values. Its module-level surface is integers and pure functions ONLY.
4. `teach_persona` -> `phase14_recall` (for `normalize` / `contains_value` / `score_question` during
   the calibration scoring pass) is **LAZY** - inside the scoring function, not at module level.
5. `phase14_recall` -> `teach_persona` (for `COLLAPSE_PPL_TRIGGER` in `run_collapse_control`) is
   **LAZY** - inside `run_collapse_control`, not at module level.

**Why both cross-script edges are lazy.** Rules 4 and 5 are a genuine cycle: `teach_persona` needs
the scoring rules, and `phase14_recall` needs the collapse trigger. Making either edge module-level
is a plain `ImportError` / partial-module `AttributeError`. Making rule 5's edge module-level ALSO
drags `teach_persona -> phase14_factset -> LOCKED_VALUES` into `personalize_demo`'s address space,
which breaks D-19, threat T-14-17, and 14-08's must-have that the demo process holds no locked fact
value.

**The cheap wrong fix, named so nobody discovers it at 3am:** duplicating `COLLAPSE_PPL_TRIGGER` as a
literal inside `phase14_recall` also breaks the cycle - and silently breaks 14-10's claim that
"applying the same threshold here keeps the two measurements on one scale," because the calibration
verdict and the phase's collapse control would then be two independently-editable numbers. One
definition, imported lazily. Do not duplicate it.

**Enforcement, not prose.** After an `importlib` load of `phase14_recall`, BOTH
`"phase14_factset" not in sys.modules` and `"teach_persona" not in sys.modules` must hold
(`tests/test_phase14_scoring.py::test_no_fact_strings_at_import`). The same pair must hold after an
`importlib` load of `personalize_demo`
(`tests/test_phase14_demo.py::test_demo_process_is_fact_free`).
</import_topology>
