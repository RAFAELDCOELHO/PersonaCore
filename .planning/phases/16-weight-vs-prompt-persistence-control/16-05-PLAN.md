## Why the grid is 2-D, restated so the material is built for the right question (D-11)

The real values are 4-8 tokens over a 547-id near-character vocabulary in a 6-layer model.
Reproducing one is NOT single-token copying — it is sustained induction, materially harder than the
"distance ~2" intuition suggests, and that is why span length entered the ladder. A distance-only
ladder would fail at every distance without distinguishing "cannot copy 5 tokens" from "cannot use
context", and those two license different headlines.

The framing is fixed and natural in every cell. An instructed-copy rung ("repeat this: X") is out
of distribution for a TinyStories+PersonaChat model, so its failure cannot separate incapacity from
instruction-following failure — and therefore licenses nothing.

## The distance-~2 blind spot the executor must not re-open (RESEARCH, Ladder wiring)

`build_recall_prompt(tok, question, persona)` emits `<|system|>persona<|user|>question<|assistant|>`
and truncates at the assistant trigger. A value in the persona span sits ~30 tokens from the
trigger (prompt is 46 tokens with a 13-token persona). To sit ~2 tokens from the trigger the value
must be at the END of the user turn — carried by the `question` string, not by `persona=`.

Consequence: **the distance-~2 rungs are INVISIBLE to the widened `persona=` guard.** The
`assert_value_in_prompt` twin from 16-02 and the every-`draw_all`-asserts guard from 16-03 are what
cover them. This is not a gap to be fixed by extending the `persona=` guard — that guard keys on an
argument name, and these call sites do not use the argument. Write the allowlist rationale in
`tests/test_phase14_scoring.py` accordingly.

## Pitfall 5, settled — do not re-litigate

Any ASCII synthetic string is generatable. 7,645 of 8,192 ids are masked as `forbid_ids`, but all
256 byte ids are live and BPE falls back to bytes for anything unmerged, so `encode()` can never
emit a dead id — the dead ids are unreachable *merges*, not unreachable bytes. Token-length matching
still matters (D-12) and is done with `token_census`.

## Task 2 runs the REAL model — wall clock and how to launch

`--vet` is **not** a CPU-only command. It loads the base model and probes every candidate:
3 spans x >= 12 candidates = **>= 36 candidates**, x 4 reserved probe questions x `PROBE_SEEDS = 4`
x `PROBE_MAX_NEW_TOKENS = 32` ~= **576 completions**, plus model load. Against the recorded medians
that is roughly **15-25 min**.

**The Bash tool's maximum timeout is 10 minutes.** A foreground `--vet` call WILL be killed mid-run
and leave a partial `results/phase16_ladder_material.md` — which is worse than no file at all,
because a truncated material report still reads as evidence and its missing rows look like
candidates that were never proposed. Launch it in the BACKGROUND and poll, exactly as 16-07 and
16-11 do for their runs.

Redirect the raw output to **`/tmp/phase16_vet.log`**, not into `results/`. The committed audit
record for this run is `results/phase16_ladder_material.md`, which already carries every candidate
with its measured token count, probe count and verdict; a second raw log inside `results/` would
break this plan's `git status --porcelain results/` check for no added evidence.

Budget **15-25 min**. A 25-minute run is expected, not a hang. Do not shrink the candidate pool to
make the clock fit — the pool is oversized on purpose (Task 1) so the gate can reject without
leaving a hole.
