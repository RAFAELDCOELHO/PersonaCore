## Wall clock and how to launch

Ladder at `n = 216` per rung: **7 rungs total** — 6 synthetic cells plus the top rung, which IS
one of the 7, not an eighth. 7 x 216 x ~3.18 s median ≈ **80 min**; the top rung's own share is the
~12 min already inside that 80, not an addition to it. (An earlier draft double-counted it as
"80 min plus 12".) The ~90 min ±15% figure the polling loop uses is unchanged and remains the
operative number. Treat the estimate as ±15% — CONTEXT.md records an 11.5% cross-run spread on arm A's
mean that exceeds the intra-run 95% CI (±4%), so the intra-run interval understates real
uncertainty and must never be quoted alone.

**The Bash tool's maximum timeout is 10 minutes.** Launch the run in the background with output
redirected to `results/phase16_ladder_raw.log`, then poll the log. Do not attempt a foreground call.

## The phase gate is stricter than the default

The full CPU suite must be green **before this run starts**, not merely before `/gsd:verify-work`.
PERS-01 makes the ladder blocking, so a ladder run on an unvalidated instrument is unrecoverable —
the numbers cannot be re-derived after the fact without breaking pre-registration.

## What counts as a normal outcome

**All cells failing is a NORMAL, pre-registered outcome** (RESEARCH Q2, D-14). Phase 14 measured
1 of 216 questions on this exact model with this exact prompt builder. If every rung fails, the
report records the `no_rung_passed` branch and the phase proceeds — licensing only the SC1
capability-deficit statement. Do NOT investigate the instrument, re-run with different settings, or
add a branch. "Not demonstrable" is a legitimate recorded result in this project, exactly as Phase
12 recorded `λ*=None`.

The instrument-broken signal is **non-monotonicity** — a harder cell passing while an easier one
fails. That is recorded as a named anomaly, in the report, without stopping the run.

## Do not

- Do not amend `results/phase14_recall_report.md`. D-19: the PERS-05 fix changes which seeds are
  drawn, so the committed `1/1944` does not reproduce bit-for-bit. That is the defect being fixed,
  and the committed Phase 14 number stays as published.
- Do not touch `LADDER_FLOOR_*` or `LADDER_CELL_PASS_K` after seeing a number.
- Do not re-run to "get a better number". A second run over a committed verdict is blocked by
  `assert_ladder_report_not_clobbered()` and would be evidence destruction if forced.
